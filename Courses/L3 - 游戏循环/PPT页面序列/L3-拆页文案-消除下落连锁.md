## A1 · 认识 Tween + 为什么不用 AnimationPlayer

**标题：** 认识 Tween：电脑自动补全"中间画"

**页面内容（概念 + 对比）：**

```
补间动画（Tweens）用于在数值范围内对数字属性进行插值的动画。
Tween 来源于 inbetweening（中间画）：你只指定关键帧，
电脑自动计算并补全过渡帧。（摘自官方 wiki）

例：position 从 (100,100) 到 (300,100)，0.15 秒
  → 电脑自动补出中间所有位置 → 看起来就是"滑动"

为什么不用 AnimationPlayer？
  · AnimationPlayer 的动画要在编辑器里提前"做"好、存进库里
  · 我们的宝石"落几格 / 移多远"是对局中算出来的——
    没法提前设计 → 用代码驱动的 Tween（写一行生成一段动画）
```

**人话（概念三要点）：**
1. **Tween = 动画调度器**：`tween_property` 让属性随时间平滑变化；你写"起点/终点/时长"，中间帧电脑算
2. **做出来的 vs 算出来的**：动画内容固定 → AnimationPlayer；动画参数运行时变 → Tween
3. 本课所有动画（消除/下落）都用它；L2 的交换动画（`board._animate_swap_pair`）也是它

**讲师口播：**
- 认识今天的明星——**Tween**。名字来自"inbetweening（中间画）"：老动画师画关键帧，助手补中间帧——Tween 就是那个助手
- 有人会问：Godot 不是有 AnimationPlayer 吗？关键区别：**动画是"做出来的"还是"算出来的"**。我们的宝石掉几格、移多远**对局中才知道**，没法学前设计——所以用 Tween：一行代码，运行时生成动画
- 代码套路固定三步：**create_tween 开调度器 → tween_property 改属性 → await 等播完**

**验证点：** 能说出"Tween 帮你做了什么"（补中间帧）+ 为什么不用 AnimationPlayer（数值运行时才确定）。

## A2 · animate_clear 精讲：await = 动画的刹车 ⭐

**标题：** animate_clear：消除动画 + T3 模板（await = 刹车）

**代码块 → 📌 归属：gem.gd → ④ 动画（唯一动画函数，8 行）：**

```gdscript
## 动画：消除（缩小到 0.2 倍 + 淡出到透明，0.2 秒，同时进行）
func animate_clear() -> void:
	var tween := create_tween()
	tween.set_parallel(true)                    # 并行：缩小和淡出一起播
	tween.tween_property(self, "scale", Vector2(0.2, 0.2), 0.2)
	tween.tween_property(self, "modulate:a", 0.0, 0.2)   # 透明度
	await tween.finished      # ← T3 模板：等这组播完
```

**人话（T3 模板，可背）：**
- **`await tween.finished` = 动画的刹车**：播完之前，代码停在这行不往下走
- **一个动画内部可以并行**：`set_parallel(true)` 后缩小和淡出**同时**进行（0.2 秒后既小又透明）
- **动画之间必须串行**：两段动画都改 position，不能同时改——同一颗宝石被两个 Tween 控制必然穿帮
- `modulate:a` = 透明度通道，0.0 = 完全透明——配合缩小就是"缩小消失"

**讲师口播：**
- gem.gd 里**唯一**的动画函数就是它（交换/下落动画由 board 统一调度）——把它读透，Tween 就通了
- **T3 模板（全课最该背的一句）：`await tween.finished`**——L2 交换动画（`_animate_swap_pair`）其实已经 await 过，今天正式命名
- 两个层面别混：**一个动画内部**可以并行（缩小+淡出一起），**动画之间**必须串行（await）——类比：一个人可以边走边挥手，但两个人开同一扇门要一个个来
- 这个函数在哪儿被调？`clear_matches`（第二部分 K1 组装）——**gem 提供能力、board 统一调度**

**验证点：** 能指出三步代码（create_tween / tween_property / await）+ 说出 T3 模板含义。

## F3 · 代码②：压实核心（代码顺序第 2 段）

**标题：** fall_and_refill ② 压实：自下而上，一格只填一次

**代码块（代码顺序第 2 段）→ 📌 归属：board.gd ⑪ 下落填充：**

```gdscript
		for row in range(GRID_SIZE - 1, -1, -1):   # 自下而上扫
			var gem: Gem = grid[col][row] as Gem
			if gem == null: continue
			if write_row != row:            # 下面有洞 → 搬下去
				grid[col][row] = null
				grid[col][write_row] = gem
```

**配图（自下而上演示，行 0 = 顶部，行 5 = 底部）：**

```
扫描前：                          压实后：
行 0: [空]                        行 0: [空]  ← 顶部空出，待补新
行 1: [绿]                        行 1: [空]
行 2: [红]                        行 2: [空]
行 3: [空]                        行 3: [绿]  ← 绿搬到 write_row=3
行 4: [蓝]  ← 扫描方向（从底往上）  行 4: [红]  ← 红搬到 write_row=4
行 5: [空]  ← write_row=5 起点    行 5: [蓝]  ← 蓝搬到 write_row=5
```

**人话（两个要点）：**
1. **自下而上**：`write_row` 落点指针从底往上走，扫到的宝石有洞就搬下去——**每个空洞只被填一次**（从上往下扫会卡半路）
2. **数据先行**：grid 表先更新（原位置清空、新位置填入）——数据先动，动画后播（L2 老套路：数据与表现分离）

**讲师口播：**
- 第二段：**压实核心**——内循环自下而上扫，宝石下面有洞（`write_row != row`）就搬下去
- **为什么必须自下而上？** 从上往下扫，上面的宝石搬下去填洞后"落点"计算就乱了——自下而上 = 每个空洞只被填一次，稳
- **数据先搬**：`grid[col][row] = null`（原位置清空）、`grid[col][write_row] = gem`（新位置填入）——画面还没动，数据先动（下一页记一笔动画账）

**验证点：** 能回答"为什么自下而上"（每个洞只填一次）。

## F4 · 代码③：时长 + 记账（代码顺序第 3 段）

**标题：** fall_and_refill ③ 按格数算时长：落得远，花得久

**代码块（代码顺序第 3 段）→ 📌 归属：board.gd ⑪ 下落填充：**

```gdscript
				var cells: int = write_row - gem.grid_pos.y
				gem.grid_pos = Vector2i(col, write_row)
				var duration := maxf(FALL_PER_CELL, float(cells) * FALL_PER_CELL)
				movers.append({
					"gem": gem,
					"target": grid_to_world(Vector2i(col, write_row)),
					"duration": duration,
				})
			write_row -= 1
```

**人话（两个要点）：**
1. **时长按格数**：落 1 格 0.08s、落 3 格 0.24s——格数 × 0.08 秒/格，**恒速**，看起来像真的重力
2. **maxf 保底**：取较大者，动画不会短到"瞬移"；**记账**：`movers.append` 把"谁/去哪/多久"记进账本（**多行字典写法**——和教学版源码一致，学员版可能是单行压缩版，语义相同，照抄多行即可）

💡 **呼应 F2 的记账本配图**：这行 `movers.append({...})` 就是 F2 那张表的**写入动作**——`gem` = 谁、`target` = 去哪（像素坐标）、`duration` = 花多久（按格数算）。F2 看格式，这里看代码怎么把它写出来

**讲师口播：**
- 第三段：**算时长 + 记账**。`cells = write_row - gem.grid_pos.y` 是"先算落几格、再更新 grid_pos"
- **为什么按格数？** 落 1 格和落 5 格用同样时间，速度就忽快忽慢，不像重力——恒速才自然
- `movers.append(...)` 记账：谁（gem）、去哪（target）、多久（duration）——记完账，最后统一播放
- `write_row -= 1`：落点指针往上移一格，继续扫

**验证点：** 能说出"落 3 格花多久"（0.24 秒）。

## F6 · 代码⑤：补新记账 + 颜色随机（代码顺序第 5 段）

**标题：** fall_and_refill ⑤ 补货记账：随机颜色 = 连锁的源头

**代码块（代码顺序第 5 段）→ 📌 归属：board.gd ⑪ 下落填充：**

```gdscript
			gem2.position = grid_to_world(start_pos)
			grid[col][write_row] = gem2
			movers.append({
				"gem": gem2,
				"target": grid_to_world(target_pos),
				"duration": maxf(FALL_PER_CELL, float(write_row - start_pos.y) * FALL_PER_CELL),
			})
			spawn_index += 1
			write_row -= 1
```

**人话（两个要点）：**
1. **先放屏幕外再记账**：position 先设到起点（屏幕外）、grid 写入数据表，再记一笔下落账——和压实段**同样的记账格式**
2. **`random_gem_type()` 颜色随机** → 补完可能又凑出新三消 → **连锁的源头**（第二部分 resolve_board 总装揭晓）

**讲师口播：**
- 第五段：**补新记账**。和压实段一样的套路：数据先写、账先记，动画最后统一播
- **颜色随机**——这就是连锁的源头：新宝石掉下来可能又凑出新三消，循环就再转一圈
- `spawn_index` 每次 +1：下一个补的新宝石起点更高（-2、-3…），排队落下

**验证点：** 能说出连锁的源头（补新颜色随机 → 可能再凑三消）。

## F7 · 代码⑥：统一播放 + 验证（代码顺序第 6 段）

**标题：** fall_and_refill ⑥ 播放：记账完毕，统一兑现

**代码块（代码顺序第 6 段）→ 📌 归属：board.gd ⑪ 下落填充：**

```gdscript
	if movers.is_empty():
		return
	var tween: Tween = create_tween()
	tween.set_parallel(true)
	for item in movers:
		tween.tween_property(item["gem"] as Gem, "position", item["target"] as Vector2, item["duration"] as float)
	await tween.finished
```

**人话（记账本模式，可背）：**
1. **为什么先记账后播放**：边扫边播 → 第 1 颗先落、第 5 颗后落 → 速度不一样，画面乱
2. **一个并行 Tween 一起播**：所有宝石**同时开始、同时结束**，观感统一；只 await 一次（T3 模板）
3. `movers.is_empty()` 防御：没宝石要动就直接返回，不白开 Tween

**验证（诚实版 ⚠️）：** 当前 part1 阶段——F5 运行**不报错、交换正常**（L2 成果保留）；但 **fall_and_refill 的效果暂时看不见**：它还没被调用（`resolve_board` 总装在第二部分才填，届时消除→下落→连锁全通）。课后作业①：`FALL_PER_CELL` 0.08→0.2（等第二部分做完下落再改，感受"手感"）。

**讲师口播：**
- 最后一段：**统一播放**——记账本模式的兑现时刻
- **为什么先记账后播放？** 边扫边播的话，第 1 颗先落、第 5 颗后落，速度不一样，画面乱——一起播才整齐
- 验证：F5 跑起来，制造三消看完整循环；作业改 `FALL_PER_CELL`——**一个数字，游戏的"手感"就变了**

**验证点：** 能说出记账本模式的好处（同时开始同时结束 + 只 await 一次）。
